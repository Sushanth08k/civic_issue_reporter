# Firestore Database Schema

## Overview
This document explains how data is structured in Firestore for the civic issue reporting system. Understanding this schema is crucial for interview prep—you'll need to explain trade-offs, scaling, and query patterns.

---

## Collections

### 1. `users` Collection
Stores user metadata and admin roles.

**Document ID:** Firebase Auth UID

```javascript
{
  uid: "user123",
  email: "citizen@example.com",
  displayName: "John Doe",
  role: "citizen", // "citizen" or "admin"
  createdAt: "2025-01-15T10:30:00Z",
  lastLogin: "2025-01-20T14:45:00Z"
}
```

**Why this structure?**
- Centralizes user metadata separate from complaints.
- `role` field enables quick RBAC (role-based access control).
- `lastLogin` helps track user engagement (analytics feature).

**Query example:** Get all admin users
```javascript
db.collection('users').where('role', '==', 'admin')
```

---

### 2. `complaints` Collection
Stores all civic issue reports.

**Document ID:** Auto-generated by `addDoc()` or custom ID

```javascript
{
  id: "complaint-abc123",
  userId: "user123",
  issueType: "Pothole",
  description: "Large pothole on Main Street",
  location: {
    lat: 40.7128,
    lng: -74.0060,
    address: "123 Main Street, City, State"
  },
  imageUrl: "https://firebasestorage.googleapis.com/...",
  status: "Submitted", // "Submitted" | "In Progress" | "Resolved" | "Rejected"
  complaintLetter: "To the Municipal Authority, ...",
  assignedTo: "admin-user-456", // Admin who is handling this
  notes: [
    {
      authorId: "admin-user-456",
      authorName: "Jane Smith",
      text: "Inspected the location. Damage confirmed.",
      createdAt: "2025-01-18T09:00:00Z"
    }
  ],
  createdAt: "2025-01-15T10:30:00Z",
  updatedAt: "2025-01-18T09:00:00Z",
  resolvedAt: null // Set when status becomes "Resolved"
}
```

**Why this structure?**
- `userId` links complaint to the citizen.
- `assignedTo` links complaint to the admin handling it.
- `status` field enables filtering (show me all "In Progress" complaints).
- `notes[]` is an array of comments—better than a separate subcollection for small amounts of data.
- `createdAt`, `updatedAt`, `resolvedAt` allow time-based analytics and sorting.

**Query examples:**
```javascript
// Get all complaints for a citizen
db.collection('complaints').where('userId', '==', 'user123')

// Get all unresolved complaints
db.collection('complaints').where('status', '!=', 'Resolved')

// Get complaints assigned to an admin
db.collection('complaints').where('assignedTo', '==', 'admin-456')

// Get complaints sorted by most recent
db.collection('complaints').orderBy('createdAt', 'desc')
```

### 3. `authorities` Collection (Optional, for future)
Stores metadata about municipal authorities/departments.

```javascript
{
  id: "authority-pothole",
  name: "Roads & Infrastructure",
  email: "roads@municipality.gov",
  phone: "+1-555-1234",
  jurisdiction: "downtown",
  assignedAdmins: ["admin-456", "admin-789"],
  avgResolutionTime: 7 // days

```

**Why later?**
- Enables complex assignment logic (route potholes to Roads dept, streetlights to Lighting dept).
- Useful for reporting and SLA tracking.

## Firestore Security Rules

**Key rule:** Only authenticated users can read/write, and admins can update any complaint.

```javascript
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    // Users collection: only own user can read, admins can read all
    match /users/{userId} {
      allow read: if request.auth.uid == userId || 
                     get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';
      allow write: if request.auth.uid == userId;
    }

    // Complaints collection
    match /complaints/{complaintId} {
      // Citizens can read their own complaints
      // Admins can read all complaints
      allow read: if request.auth.uid == resource.data.userId || 
                     get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';

      // Citizens can create complaints
      // Admins can update status, assignment, notes
      allow create: if request.auth != null && request.resource.data.userId == request.auth.uid;
      allow update: if get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';
      allow delete: if false; // Never delete complaints (audit trail)
    }
  }
}
```

## Interview Questions on This Schema

### Q1: "Why store `assignedTo` directly on the complaint instead of a separate 'assignments' collection?"
**Answer:** For this use case, a complaint has one admin at a time. Storing it directly on the complaint document:
- Reduces queries (1 read instead of 2)
- Keeps related data together
- Simple to update
- No need to manage a separate relationship

**Trade-off:** If one complaint could have multiple admins or if assignments were frequent/temporary, a subcollection would be better.

### Q2: "What if there are thousands of notes on one complaint?"
**Answer:** An array in Firestore can grow without limit, but:
- Document size limit is 1MB
- Reading the entire complaint fetches all notes
- Each write to notes rewrites the whole array

**Solution:** Move `notes` to a subcollection: `complaints/{id}/notes/{noteId}`
This allows:
- Pagination of notes
- Atomic writes without rewriting the entire complaint
- Better query patterns (get first 10 notes)

### Q3: "How do you query 'all complaints assigned to me'?"
**Answer:**
```javascript
db.collection('complaints')
  .where('assignedTo', '==', adminUserId)
  .orderBy('createdAt', 'desc')
  .limit(20)
```

This leverages the `assignedTo` index for fast queries.

### Q4: "How do you prevent admins from seeing citizen email addresses?"
**Answer:** Firestore security rules check the user's role before granting read access:
```javascript
allow read: if get(/databases/$(database)/documents/users/$(request.auth.uid)).data.role == 'admin';
```

Only admins can read the `users` collection.

## Scaling Considerations

### Current (small dataset)
- Collections fit in memory
- Queries are fast
- No indexing complexity

### 10K+ complaints
- Add composite indexes on frequently queried fields: `status + createdAt`, `assignedTo + status`
- Consider moving notes to subcollection
- Add a `lastUpdated` field for sorting performance

### 1M+ complaints
- Partition data by time (archived complaints go to `complaints_archived_2024`)
- Consider Firestore's real-time listeners may become expensive
- Add counters collection for analytics (count of resolved complaints, etc.)

---

## Why This Matters for Interviews

1. **Schema design reflects system thinking:** Good schemas anticipate queries, scale, and consistency.
2. **Tradeoffs:** You make conscious choices about denormalization (storing `assignedTo` vs. a join).
3. **Query patterns:** Interviewers ask "How do you fetch X?" Your schema either makes it easy or requires complex client-side filtering.
4. **Security:** Rules + schema together prevent unauthorized access.
5. **Performance:** Proper schema design reduces reads/writes and costs.
